What the template actually does with a scan

  • Receives the OEM broadcast. A manifest receiver listens for the action you set in config.json, so Zebra, Honeywell and Datalogic fleets use the same build.
  • Writes into the live control. The value is set through the native input setter and fired as input and change, which is what Power Apps text inputs listen for.
  • Never navigates. No reload, no ?barcode= query parameter, so an in-progress form survives a hundred scans in a row.
  • Always leaves a hook. Every scan also lands in window.__LAST_BARCODE__ and fires a barcodeScanned event for custom screens.

One file

Everything is config.json

Six keys. The file is compiled into the APK, so there is nothing to copy onto the device and nothing for an operator to edit.

Keys

KeyWhat it does
appNameName on the device launcher, the task switcher and the splash.
powerAppUrlThe Power Apps link that opens on launch. Use the /play/ URL, not the editor.
keepScreenOnStops the display sleeping mid-shift.
interceptBackButtonSwallows the hardware and gesture Back button so nobody backs out of the app.
scanner.intentActionThe broadcast action the scan engine sends. Must match the device profile exactly.
scanner.intentExtraKeyThe string extra carrying the barcode. Zebra uses com.symbol.datawedge.data_string.
allowedDomainsDomains allowed to load in the viewport. Subdomains are included; everything else is blocked.

The shipped default

{
  "appName": "PowerApps Handheld Shell",
  "powerAppUrl": "https://apps.powerapps.com/play/e/…",
  "keepScreenOn": true,
  "interceptBackButton": true,
  "scanner": {
    "intentAction": "com.powerapps.handheld.SCAN",
    "intentExtraKey": "com.symbol.datawedge.data_string"
  },
  "allowedDomains": ["apps.powerapps.com", "…"]
}

Bad JSON, a missing key or a malformed URL fails the build instead of shipping.

Hardware

Point the scan engine at the app

The scan engine has to broadcast. Most rugged handhelds ship with one; the profile is what connects it to this APK.

1

Open the scan profile

On Zebra that is the DataWedge app, then the profile your app runs under.

2

Turn on intent output

Enable Intent output, set delivery to Broadcast intent, and clear the category field.

3

Match the action

Set the intent action to the same string as scanner.intentAction. Zebra keeps the payload key as-is.

Honeywell and Datalogic work the same way with their own broadcast settings. If a device sends a different extra key, change scanner.intentExtraKey and rebuild: the receiver also falls back to the common version_1_data and data extras.

Keyboard-wedge mode is not used. Held keys, dropped characters and focus jumps are exactly what a broadcast intent avoids.

Honest limits

What this template is not

Small on purpose. Every extra feature is memory and support on a device that has neither to spare.

Not a device-owner kiosk

It hides the system bars and swallows Back. It does not lock the device down at the OS level; that stays with your MDM.

Not a camera scanner

Hardware scan engines only. No CameraX, no ML Kit, no photo permissions.

Not an offline cache

Power Apps owns its own offline data. The shell adds no database and no sync layer.

Not multi-app

One Power App, one window, no tabs or split view. Copy the template again for a second app.

Builds

Where the APK comes from

Ubuntu runner, JDK 17, Android SDK and NDK, Rust targets for 64-bit and 32-bit ARM.

Every run verifies its own artifact before publishing: the APK is checked for a valid signature, both ARM libraries, the barcode receiver in the merged manifest, and the compiled-in config.json. A build that produces a broken APK fails instead of looking green.

Each green build on main publishes the next numbered release with the APK attached, so there is always a downloadable file rather than an artifact that expires. Documentation commits do not cut a release.
